# 注释与可读性规范

> 范本：[`tests/01-basics/01-structure-demo.spec.ts`](../tests/01-basics/01-structure-demo.spec.ts)——第 1 课的逐行学习注释，本项目注释风格的事实标准。新代码（无论人写还是 agent 写）都按这个风格来。

## 七条原则

1. **解释意图，不翻译代码**。好注释回答「为什么这么做」，而不是复述语句在干什么。
   - 好：`// 把要校验的区块标题放进数组，用 for 循环逐个断言——避免重复 7 遍几乎一样的代码`
   - 差：`// for 循环断言七个标题`

2. **新 API / 新概念首次出现时，以「API 名：作用」开头**，随后补关键参数与行为细节：
   ```ts
   // getByRole('navigation')：按「无障碍角色」定位导航栏（对应 <nav>）。
   // 这是 Playwright 推荐的首选定位方式——稳定、贴近真实用户/读屏软件视角。
   ```

3. **写清行为后果**。凡是「代码顺序影响执行」的地方，注明效果：
   ```ts
   await page.goto('/'); // 因为上面 skip(true)，这一行永远不会执行
   ```

4. **用横线分块组织文件**，每块一个概念，块首两三行说明：
   ```ts
   // ─────────────────────────────────────────────────────────────
   // describe：把一组相关的测试用例「打包」成一个分组（在报告里是层级目录）
   // 第一个参数是分组名（中文也可），便于 --grep 按名字筛选、报告里归类。
   // ─────────────────────────────────────────────────────────────
   ```

5. **测试文件头部用 JSDoc 块**：本文件主题 / 配套讲义或文档 / 可直接复制的常用跑法。

6. **中文为主，API 名、术语、标识符保留英文**（getByRole、fixture、baseURL…），方便对照官方文档。

7. **注释密度分级**：
   - `tests/`、`lessons/` 的教学与示范代码：按范本密度从密；
   - `demo-app/`、`scripts/`、配置文件等工程代码：只在约束不明显处注释（如「为什么必须这样」），不逐行。

## 适用范围

- 所有人与所有 agent（AGENTS.md 已引用本规范）；
- Code Review / 验收时，注释风格与 lint 同为检查项。
